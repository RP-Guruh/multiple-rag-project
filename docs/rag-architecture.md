# RAG Pipeline Architecture & Design Concept
**Project:** DevLab LM (Spring Boot + JavaFX Desktop)  
**Objective:** Ingest uploaded documents into vector embeddings for semantic retrieval.

---

## 1. Overview & Pipeline Flow

The RAG (Retrieval-Augmented Generation) pipeline starts after files have been successfully uploaded (`status = 'UPLOADED'`). When the user clicks **Start Training**, a background worker processes unprocessed documents through five sequential stages:

```text
+-------------------+
|  Uploaded File    | (Stored at: data/projects/{id}/docs/{uuid}_{filename})
+---------+---------+
          |
          v
+---------+---------+
|  1. Extraction    | Extract raw plain text based on file format
+---------+---------+
          |
          v
+---------+---------+
|  2. Chunking      | Split text into overlapping segments
+---------+---------+
          |
          v
+---------+---------+
|  3. Embedding     | Convert text chunks into float vectors via AI API
+---------+---------+
          |
          v
+---------+---------+
|  4. pgvector Store| Persist chunks and vectors to PostgreSQL
+---------+---------+
          |
          v
+---------+---------+
|  5. Query / Chat  | Cosine similarity search injected into LLM Prompt
+-------------------+
```

---

## 2. Ingestion Stages

### Stage 1: Document Text Extraction
Inspects `document.file_type` and selects the appropriate parser:

| Format | Library | Strategy |
| :--- | :--- | :--- |
| **PDF** (`.pdf`) | Apache PDFBox | Read pages sequentially; clean form-feeds and trailing whitespaces. |
| **Word** (`.docx`, `.doc`) | Apache POI (`XWPFDocument`) | Extract paragraphs, headings, and table cells. |
| **Excel** (`.xlsx`, `.xls`) | Apache POI (`XSSFWorkbook`) | Extract tabular data as structured TSV/Markdown representations. |
| **Text** (`.txt`, `.md`, `.csv`) | Native Java NIO | Direct UTF-8 decoding. |

### Stage 2: Text Chunking Strategy
Raw extracted text cannot be sent to LLMs as a single blob due to token context limits and retrieval granularity.

* **Chunk Size:** 500 – 800 characters (approx. 100 – 160 tokens).
* **Chunk Overlap:** 100 characters.
  * *Purpose:* Preserves semantic context across split boundaries so sentences are not clipped abruptly.
* **Separators (Recursive Hierarchy):**
  1. Double newlines (`\n\n`) -> Paragraph boundary.
  2. Single newline (`\n`) -> Sentence/line boundary.
  3. Punctuation (`. `, `? `, `! `).
  4. Whitespace (` `).

### Stage 3: Embedding Generation
Chunks are batched and sent to the configured embedding provider (`AiSettingService`):

* **Embedding Model Options:**
  * **Ollama (Local):** `nomic-embed-text` (768 dim) or `bge-m3` (1024 dim).
  * **OpenAI (Cloud):** `text-embedding-3-small` (1536 dim).
* **Batching:** Send 20 – 50 chunks per HTTP request to optimize throughput and network overhead.
* **Output:** An array of `float[]` coordinates representing semantic meaning in vector space.

### Stage 4: PostgreSQL + pgvector Persistence
Stores generated vectors into the relational database alongside chunk text and metadata.

* Chunks are inserted in batch inside a single transaction.
* Status in `documents` transitions: `EXTRACTING` -> `EMBEDDING` -> `INDEXED` (or `FAILED` with `error_message`).

## 3. Database Schema Concept (`document_chunks`)

```sql
-- Enable vector extension
CREATE EXTENSION IF NOT EXISTS vector;

CREATE TABLE document_chunks (
    id              BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    document_id     BIGINT NOT NULL REFERENCES documents(id) ON DELETE CASCADE,
    project_id      BIGINT NOT NULL REFERENCES projects(id) ON DELETE CASCADE,
    chunk_index     INT NOT NULL,
    content         TEXT NOT NULL,
    token_count     INT,
    embedding       vector(1536),           -- Dimensions match configured embedding model
    metadata        JSONB,                  -- Optional: { "page": 3, "file_name": "guide.pdf" }
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- Indexing for fast vector similarity search:
CREATE INDEX idx_chunks_project_id ON document_chunks(project_id);
CREATE INDEX idx_chunks_document_id ON document_chunks(document_id);

-- HNSW Index for sub-millisecond approximate nearest neighbor (ANN) retrieval:
CREATE INDEX idx_chunks_embedding ON document_chunks 
USING hnsw (embedding vector_cosine_ops)
WITH (m = 16, ef_construction = 64);
```

## 4. Retrieval & Chat Inference Flow (How It's Used)

When a user asks a question in the chatbot interface:

```text
User Question: "What is the return policy for defective items?"
                      |
                      v
1. Embed Query        -> Call embedding model -> query_vector
                      |
                      v
2. Similarity Search  -> SELECT content, 1 - (embedding <=> query_vector) AS score
                         FROM document_chunks
                         WHERE project_id = :projectId
                         ORDER BY embedding <=> query_vector
                         LIMIT 4;
                      |
                      v
3. Augment Prompt     -> Inject system prompt + retrieved context chunks
                      |
                      v
4. Send to LLM        -> LLM answers strictly based on the provided chunks
```

### Prompt Construction Template
```text
System Prompt:
{project.system_prompt}

Context Information:
---------------------
[Doc: guide.pdf | Page 2]
{chunk_1_content}

[Doc: policy.txt]
{chunk_2_content}
---------------------

User Question:
{user_query}

Answer:
```

## 5. UI Integration & Feedback Loop

* **Tab 1 (Knowledge Base Table):**
  * `colStatus` displays: `UPLOADED` -> `EXTRACTING` -> `EMBEDDING` -> `INDEXED`.
  * `colChunkCount` updates from `0` to actual count.
* **Tab 2 (Training Pipeline):**
  * **Progress Bar:** Reflects batch progress: `(processed_chunks / total_chunks) * 100%`.
  * **Log Area:** Real-time log streams detailing parsing milestones, token counts, and API response latencies.
